## Description of Design
My ALU is composed of several modules: A 32 bit mux (composed of smaller muxes designed in lab). An Or and And module that simply takes inidivuals bits of the inputs A and B and Ors or Ands them together. This was implemented with a generate function to reduce repetitivness. 

I also have sll and sra implemented in very similar ways. For both, I built smaller 1, 2, 4, 8, and 16, modules to account for the maximum case of shifting a 32 bit number. For the n-bit sll, I would assign the rightmost 32-n bits as a new shifted wire. Then, if selected by the alu, I would concatonate these rightmost 32-n bits with n 0s added to the beggining of the number, which would satasfy the sll operation. In a very similar manner, for sra, I would select the 32-n leftmost bits as a new wire, and then concatonate n signed bits (depending on the MSB of the number) on the left of that number, which would then bring the total nhumber of bits back up to 32 (in both sll and sra). This process was ultimatley completed in 32 bit sla and sll files to account for the maximum number of shifts for a given 32 bit number, and the 32 bit module for each was composed of the smaller 1,2,4,8,16 bit modules for the respective operation that acted in a carry-ripple adder sense.

Other than the Alu file itself, my 2 level carry look ahead adder is the other most notable element in my ALU. In designing this, I first built a 8 bit CLA adder that would simplify the work I woulkd need to do, as I eventually connected 4 modules of the 8 bit adders to create a 32 bit adder. First, in the 8 bit module, I expanded out the carry terms with propogates and generates in order to calculate the carry bits in a way that did not require one who calcualtion to be done before the carry could be actually calculated and transfered to the next clauclation (as we would see in a carry ripple adder). The final exapansion for this module was for the last carry bit, c8, which utilized all of the propogations and generates from the previously calcualted terms in the same module. To finish this module, computing the sum was as easy as xor'ing the A and B inputs with the Carrys. I also had to calculate the Overall P_block and G_block outputs for the 8 bit adder, as these would later be used in the second layer of the CLA adder. As seen in the slides, the P_blcok would just be found by and'ing all of the previsouly found propogates, whereas the G_block would by found by and'ing the repesctive propogates with generates, then or'ing all of those calculations.

This 8 bit module took in 8 bit inputs of A and B, a Carry in, and outputted an 8 bit sum, a carry out, and the final calculted P and G blocks. In order to compute the adder for the 32 bit inputs, I needed to concatonate the 8 bit modules into 4, 8 bit modules, and this is where the seocnd layer comes in. The second layer of the CLA adder takes the reuslts from each of the 8 bit modules and combines them to form 16, 24, and finally a 32 bit adder. The process is essentially the same as descfibed above, but each G and P block outputs of the 8 bit adder are inputs to the second level where the carry signlas are computed between each 8 bit module and then fed back into the 8 bit modules. Badsically, the sums are all computed in parrelel as opposed to waitining for the carry ripple adder to ripple the carry bit, which speeds up the entire adder calculations for the 32 bit calculation! For any subtraction elements, I simply used a generate function to replace B with Not B if needed with 2s complement.

Finally, all of these modules are combined in the alu. A mux reads the alu opcode and selects which result to display. For the remanining outputa of IsLessThan, NotEqualTo, and overflow, I used boolean logic to detemrine when each of the following should or should not be true and/or false.


## Bugs
There are no bugs in my ALU. During the design process, however, did encounter one bug that threw me off a little bit. For the overflow output deisgn, i calculated the overflow for both the addition opertion (addition overflow) and the subtraction operation (subtraction overflow). Then, without thinking, I simply commanded the output for overflow to be the or of the sub or add overflow, thinking that if either one was true, there had to be an overflow, so I would output true. What I didn't realize at the time, however, was that since the ALU only selected one operation (add or subtract), that the overflow for the unused operation should not have been considered in selecting an output for overflow. This caused some gradescope test cases to fail, which let me quickly realize the issue at hand.Only the overflow calcualtion for the selected operation should have been considered for the overflow output, which was quicky fixed by adding in a mux to select the correct overflow for the given operation.
